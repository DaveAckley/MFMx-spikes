Thu Aug 28 01:28:25 2025 So we need to think
things through a bit, here. Having to do with
access to the local RAMs, which are unique per
"Baby RISCV" on the one hand, and the L1 RAM,
which is shared by five babies (B, T0, T1, T2,
NC), on the other hand.

So it doesn't make sense to have completely
separate compilation for the different babies,
because all the compiled code for all five of them
has to land in one L1 anyway.

So we should be thinking about a single image with
five entry points, and the ability to share code
arbitrarily among those five threads of control.

In particular, we'd like to be able to have
different stack sizes on the five babies, along
with utterly unique contents of each private RAM.

So for example, we could put the Mersenne twister
state (< 3KB?) in one private RAM, and have the
associated hart do nothing except generate and
dish out random numbers (perhaps via the
mailboxes?) to other harts on demand. Not sure how
slow that would be but it would get the PRNG state
into fast memory, and we'd hardly need any stack
for that hart anyway.

[20:

Thu Aug 28 02:24:08 2025 So okay: corsix confirmed
that the hw inter-RV mailboxes provide no way for
the writer to know if the mailbox is full, and
thus no way for the writer to know if the next
write will block, and thus no way for the writer
to service multiple readers on-demand.

So that's a bummer from a generality point of
view. But now I'm thinking maybe I don't really
need that generality anyway. Suppose we use RV B
for the main event transition processing, and,
say, RV T1 for the PRNG.

And then we have T1 just
 - set things up, putting an MT in its private ram
 - fill the T1->B mailbox with outbound #s,
   blocking when the mailbox is full, and mixing
   the MT between writes when the MT is empty

then B 'should' be able to pop a number on demand
almost all the time, with a buffer of four numbers
to cover some (or perhaps most?) of the mixing
time when T1 is away doing that.

Wed Sep 24 11:23:10 2025 Maybe it's two pairs of
slots, with one local slot and a matching remote
slot in each pair. The invariant is that when one
end of a pair is occupied, the other end is
reserved. When we fill a buffer we ship it back to
the matching slot and mark our end reserved. So
for the in-flight time, both ends of the slot are
marked reserved, and otherwise exactly one end is
occupied and the other end is reserved.

We have a local toggle to tell us which slot we're
currently 'operating on' - filling or emptying, I
guess - and when we ship a buffer we flip the
toggle. If the slot indicated by the toggle is
marked 'reserved', then we are blocked locally and
have to deal with that. If we've covered the
latencies effectively and sized everything for the
expected load, that shouldn't happen that often
except for bursty conditions when that's what we
should expect anyway.

The pair generalizes to an array, and the toggle
generalizes to an array index, and I guess we
could handle all the way down to an array length
of one, if we didn't care about round trip
latencies at all.

So this is like a bank of elevators. Which makes
me ask if we could have a loop of stops rather
than just point-to-point. We just need to know
where to ship an 'elevator car' when we're done
with it. And then that elevator landing is
reserved until the car comes back around.

I guess the only time that would really win is if
occupants might be getting on and off at each
stop. If everybody just wants to get to the host
that means we're shipping the same data multiple
times and perhaps/presumably eating lots of
network bandwidth doing so.

..Although if the stops were spatially local, so
you're only consuming a little extra bandwidth, if
any, to send a car hopping along a local chain
picking up additional passengers.. You're
increasing the latency a lot by having the car
stop at each 'floor', but the total bandwidth
might be less, if we're paying to send whole car
units regardless of how full each is.

 tile, and writing those bytes into the address space of
 another tile. When the reads or writes are against a tile's L1,
 they will be broken up into aligned 16 byte units, where
 each read of 16 bytes is atomic, and each write of 16
 bytes is atomic, but the various reads could happen in
 any order, and the various writes could also happen in any
 order, and the reads / writes can be interleaved with other
 agents acting on L1. Software can inspect counters to
 determine once all the reads have happened or all the writes
 have happened, but should not assume anything about the order
 in which the individual reads or writes happen, other than
 the one scenario outlined in the next paragraph.

 For writes to L1, the write will be decomposed into two separate
 streams by the receiving NIU: byte addresses which are between
 0 mod 32 and 15 mod 32 (inclusive) will go to stream 0,
 whereas byte addresses which are between 16 mod 32 and 31 mod 32
 (inclusive) will go to stream 1. Within each stream, ordering is
 guaranteed: the writes from a single packet will happen in
 ascending address order.
